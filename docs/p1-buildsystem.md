# P1-L — Port build system (Phase-1 skeleton)

Implements: `build/Makefile`, `build/units.txt`, `build/gen_waivers.py`,
`build/waivers/pso_assert_waivers.h`, `tools/parse_gate.py`.

## 1. How to run

```sh
make -C build parse         # syntax-only over all units; prints "== parse: TOTAL=.. FAIL=.. PASS=.."
make -C build list-fail     # -> build/parse_fail.txt (sorted failing-unit paths)
python3 tools/parse_gate.py # regression gate at the 669 baseline; nonzero exit on drop
make -C build parse-lp64    # same sources under the real LP64 link triple
make -C build smoke-link    # compile+link+exec proof of the LP64 toolchain (build/bin/host_smoke)
```

Portability contract: the decomp checkout is the single variable
`DECOMP_ROOT` (default `$(HOME)/Hermes/pso-decomp/pso-decomp`, override with
`make -C build parse DECOMP_ROOT=...` or the env). `build/units.txt` is
regenerated by `find src \( -name '*.cpp' -o -name '*.c' \) | sort` relative to
that root — the committed copy is a snapshot of `pso-decomp @ 6b38b5383`
(1680 units). The Makefile never writes into `DECOMP_ROOT`; all artifacts land
in `build/parse/`.

Compile flags are the exact set proven by `probes/tree_compile_probe.sh`
(669/1680 @ arm64_32): `clang++ -fsyntax-only -std=c++17 -w -fms-extensions
-target <PARSE_TARGET> -ffreestanding -Wno-c++11-narrowing` (`.c`: `-std=c11`),
force-including `compat/pso_metal_compat.h` and then
`build/waivers/pso_assert_waivers.h`, with the decomp `-Iinclude -Iinclude/clib
-Ilibs/dolphin/include -Ilibs/dolphin/include/dolphin -Isrc`. WHY: see the two
rationale comments in the probe (freestanding `void main`, MWCC `case -1:` wrap).

## 2. Parse baseline gate

`tools/parse_gate.py` runs `make -C build parse`, extracts `PASS=n` from the
summary line, and exits nonzero if `PASS < PSO_PARSE_BASELINE` (default **669**,
Phase 0's achievement). It prints `delta=<actual-baseline>` either way, so an
improvement is visible before the baseline is raised.

### Measured on `pso-decomp @ 6b38b5383` (2026-11-26)

Two real measurements were taken as the tree and lane I moved under this build:

* Waiver-inert phase (TSV present but 0 RUNTIME-WAIVE rows):
  `TOTAL=1680 FAIL=1012 PASS=668`, gate exit 1 (`delta=-1`).
* Final state (lane I committed 34 RUNTIME-WAIVE types; waiver header ACTIVE,
  103/3317 asserts neutralized — exactly lane I's published "103 names"):

```

parse_gate: baseline=669  actual=1416/1680  delta=+747
parse_gate: OK — at or above baseline (+747 improvement).                       (exit 0)
```

1416 sits inside Phase 0's projected 1580-after-assert-policy band. The −1 seen
while waivers were inert was **decomp-tree drift, not build drift**, proven two
ways:

* Re-running `src/pso/unk/TLobby_80228C84.cpp` with the *bare probe command*

  `LAYOUT_ASSERT(PlayerActionPaletteTagOffset, ...)` was added by PR #406,

* Comparing failure sets on the 1664 units present in both the probe and now:

## 3. FAIL-CLOSED assert waivers

`data/assert-verdicts.tsv` (lane I) has columns
`type asserts failing verdict evidence-file`. `build/gen_waivers.py`:

1. Enumerates every `LAYOUT_ASSERT(<name>, <cond>)` in `include/` + `src/`
   (3317 names at 6b38b5383 after joining backslash-continuations), resolving
   the `##_field` helper macros (`CHAT_OFFSET`, `DRAGON_OFFSET`,
   `TRADE_MESSAGE_OFFSET`, `MOJA_OFFSET`, `FIREWORK_OFFSET`, …) to their
   concrete invocation names, and maps each assert to the type its
   condition tests (`sizeof(T)` / `offsetof(T,f)`).
2. Waives **only** types whose verdict column contains the canonical marker
   `RUNTIME-WAIVE` (lane I labels rows e.g. `RW (RUNTIME-WAIVE)`). Any other
   value — `FORMAT-KEEP`, `UNREVIEWED`, `NOT-AT-FAULT`, `CONFLICT`, typos,
   future unknowns — is kept. **A FORMAT-KEEP type can never be waived:**
   `FORMAT-KEEP` is matched first with absolute precedence (`continue`), so a
   row containing it never reaches the waiver branch even if mislabeled with
   both markers, and a type with contradictory verdict rows across the file is
   kept with a warning (fail-closed).
3. TSV absent → writes a **no-op header** (`#define PSO_ASSERT_WAIVER_ACTIVE 0`
   only) and prints `gen_waivers: NO VERDICTS YET — ... Asserts stay fully
   active.` Zero RUNTIME-WAIVE rows → same no-op header (that is today's real
   state: 1770 verdict rows, 0 waivable).

### Mechanism (why it can't lie)

`include/types.h` defines `LAYOUT_ASSERT` **unguarded**, so a plain
force-include loses to it. When waivers ARE active, the generated header
`#include <types.h>` first (its `TYPES_H` guard turns every later source
include of it into a no-op), then `#undef`s and reinstalls `LAYOUT_ASSERT` as
a per-name dispatch:

```c
#define LAYOUT_ASSERT(nm, cond) PSO_LA_PICK(PSO_LA_FLAG_##nm)(nm, cond)
/* PSO_LA_FLAG_<nm> = 0 -> typedef char nm[(cond)?1:-1]  (honest assert)
                  = 1 -> static int pso_la_waived_<nm> = 0 (neutralized)
   undefined -> expands to a non-macro token -> compile ERROR */
```

* Unknown/unenumerated assert names **fail compilation** — a waiver can never
  accidentally swallow an assert it wasn't generated for. The generator
  re-runs on every `make parse` (target `waivers` is FORCE-phoned), so the
  flag set tracks the tree within one build invocation.
* Verified at compiler level with a synthetic RUNTIME-WAIVE TSV: a waived
  failing assert compiles; the same assert under flag 0 still fails with
  `declared as an array with a negative size`; an unenumerated name fails with
  a hard compile error. (3 TUs, arm64_32, real flag set.)
* With zero waivers the header is inert, so the 669/668 baseline numbers above
  are **without any waiver effect** — parse honesty is the default state.

Residual known limits: an assert whose type cannot be parsed from the cond
(`None` type) is always kept; pasted helper names that aren't a simple
identifier argument stay fail-closed with a generator warning.

## 4. Parse-target vs link-target

The 669 gate is **arm64_32 ILP32** (`-target arm64_32-apple-watchos7.0`) — a
measurement triple only; it cannot produce a linkable macOS binary. The Phase-1
boot slice **really executes as LP64 arm64 Apple silicon**, where pointer and
`long` widths move layouts differently (this is also why lane I re-measured
assert failures under LP64 rather than reusing docs/abi.md's ILP32 list).

Consequences encoded in the build system:

* `PARSE_TARGET` (default arm64_32) drives `parse`/`list-fail` and the gate.
* `LINK_TARGET` (default `arm64-apple-macos12.0`) drives `parse-lp64` and
  `smoke-link`; real object compilation/linking for the boot slice uses it.
* The two modes must not be averaged or conflated: at 6b38b5383 both *count*
  668 units, but their pass sets differ on **598 units** — a count match is
  coincidence, and only the LP64 set predicts what the boot slice will compile
  AND link. Expect the waiver lane's work (RUNTIME-WAIVE verdicts) to lift the
  LP64 number first; arm64_32 remains the historical baseline gate.
